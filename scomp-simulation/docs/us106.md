# US106 - Function-specific parent threads

The hybrid simulator implements US106 in the parent process. The parent process creates dedicated threads for separate simulation responsibilities while flight execution remains isolated in child processes.

## Thread architecture

The parent process creates three function-specific threads:

- `scheduler_thread_main`: controls timestep progression and releases child flight processes through semaphores.
- `safety_thread_main`: monitors the synchronized position data produced from shared memory and detects safety violations.
- `report_thread_main`: waits for report events and updates the runtime simulation report.

The flight processes write their `position_update_t` records into the shared memory region created with `shm_open`, `ftruncate` and `mmap`.

## Synchronization flow

```text
Parent process
  |
  |-- scheduler thread
  |     1. sets shared->current_step
  |     2. releases each flight process with semaphores
  |     3. waits until every flight posts an update
  |     4. copies shared memory updates into position_history
  |     5. releases the safety thread for that timestep
  |
  |-- safety detection thread
  |     1. waits for scheduler timestep completion
  |     2. scans the synchronized position history
  |     3. detects conflicts through safety_monitor
  |     4. sends SIGUSR1 to involved flight processes
  |     5. notifies the report thread through condition variables
  |
  |-- report generation thread
        1. waits on the report notifier condition variable
        2. consumes safety violation events
        3. updates simulation_report_t
        4. writes the final report when the simulation ends
```

## Shared memory access

Child flight processes write positions into:

```c
shared->updates[flight_index][step]
shared->received[flight_index][step]
```

The scheduler thread waits for all children with `hybrid_sync_wait_for_updates` before reading those shared memory slots. This creates a semaphore-based barrier, so the safety thread only sees a complete and consistent timestep snapshot.

## Mutex and condition variables

The parent thread state uses a mutex to protect scheduler/safety progress fields:

```c
last_completed_step
last_safety_processed_step
scheduler_finished
safety_finished
```

Safety-to-report communication is implemented by `safety_report_notifier_t`:

- the safety thread calls `safety_report_notifier_notify`;
- the notifier locks a mutex, appends a report event and signals a condition variable;
- the report thread blocks in `safety_report_notifier_wait` until an event is available;
- the wait loop handles spurious wakeups safely.

This keeps inter-thread communication thread-safe and avoids race conditions around report event delivery.

## Validation

US106 is validated by the hybrid test suite:

- `tests/test_hybrid_sync.c` validates semaphore synchronization primitives.
- `tests/test_safety_report_notifier.c` validates mutex and condition variable notification behaviour.
- `tests/test_hybrid_simulation.c` runs a safe hybrid simulation and verifies that the scheduler, safety and report threads complete without deadlock.

Run the validation with:

```sh
make clean
make test
make run-hybrid
```
