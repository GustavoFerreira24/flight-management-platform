# US107 - Safety violation report notification

The hybrid simulator implements US107 with a dedicated safety detection thread and a report generation thread.

## Thread communication flow

1. The scheduler thread releases each simulation timestep and waits for all flight processes to write their positions into shared memory.
2. The safety detection thread scans the shared position history after the timestep barrier is complete.
3. When a safety violation is detected, the safety thread builds a report event and enqueues it in `safety_report_notifier_t`.
4. The notifier protects the event queue with a `pthread_mutex_t` and wakes the report thread with `pthread_cond_signal`.
5. The report thread waits on the condition variable, consumes each event and appends it to `simulation_report_t`.

## Mutex and condition variable strategy

`safety_report_notifier_t` owns the synchronization state used by US107:

- `mutex` protects `events`, `event_count`, `next_event` and `closed`.
- `condition` blocks the report thread until at least one event is available or the notifier is closed.
- `safety_report_notifier_notify` locks the mutex, appends the event, signals the condition variable and unlocks the mutex.
- `safety_report_notifier_wait` locks the mutex and waits in a `while` loop to handle spurious wakeups safely.

This keeps report updates in the report generation thread while the safety detection thread remains responsible for detecting conflicts and notifying the report thread.

## Validation

`tests/test_safety_report_notifier.c` validates that:

- a report thread waiting on the condition variable wakes when a safety event is notified;
- the event is appended to the report by the report thread;
- closing the notifier unblocks a waiting report thread;
- invalid arguments are rejected.
